## 1. Overview

This project implements a framework for comprehending SQL queries by automatically annotating them with execution plan information. Given any SQL query over any PostgreSQL database schema, the system:

1. Retrieves the **Query Execution Plan (QEP)** — the plan chosen by the PostgreSQL optimizer.
2. Generates **Alternative Query Plans (AQPs)** by systematically disabling individual planner methods.
3. **Annotates** the SQL query to explain *how* each component is executed and *why* specific operators were chosen over alternatives.
4. Presents results through an interactive **Streamlit GUI** with color-coded inline annotations, visual plan trees, and cost comparisons.

The solution is **schema-independent** — it works on any PostgreSQL database without hardcoding table names, column names, or query structures.

## 2. System Architecture

The system follows a modular pipeline architecture with four Python files:

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  project.py  │────▶│ preprocessing.py  │────▶│  annotation.py   │────▶│  interface.py    │
│  (entry pt)  │     │ (SQL + EXPLAIN)   │     │ (plan analysis)  │     │ (Streamlit GUI)  │
└──────────────┘     └───────────────────┘     └──────────────────┘     └──────────────────┘
       │                      │                         │                        │
       │                      ▼                         ▼                        ▼
       │               ┌─────────────┐          ┌─────────────┐         ┌──────────────┐
       │               │ PostgreSQL  │          │ PlanBundle   │         │ Streamlit UI │
       │               │  Database   │          │ (QEP + AQPs) │         │ (browser)    │
       │               └─────────────┘          └─────────────┘         └──────────────┘
       │
       └──── CLI mode: prints annotated query, plan tree, AQP summary to stdout
```

**Data flow summary:**

1. User provides an SQL query (GUI text area or CLI argument).
2. `preprocessing.py` normalizes the SQL, connects to PostgreSQL, retrieves the QEP and generates AQPs.
3. `annotation.py` analyzes the plan tree, builds natural-language notes, and maps them to SQL line ranges.
4. `interface.py` renders the results with color-coded highlights, Graphviz trees, and interactive comparisons.

## 4. Key Algorithms

### 4.1 SQL Statement Splitting

**Goal:** Split a multi-statement SQL string into individual statements, respecting quotes and comments.

**Algorithm (preferred — AST-based):**

1. Parse the SQL text using `sqlglot.parse(sql_text, read="postgres")`.
2. For each AST node, regenerate the SQL and normalize it.
3. Filter out empty statements.

**Algorithm (fallback — character-level):**

```
function _fallback_split_sql_statements(sql_text):
    Initialize state flags: in_single_quote, in_double_quote, in_line_comment, in_block_comment
    Initialize current_chars = [], statements = []

    for each character ch at position i:
        if in_line_comment:
            append ch; if ch == '\n': exit line comment
        elif in_block_comment:
            append ch; if ch == '*' and next == '/': append '/', exit block comment
        elif not in any quote:
            if ch == '-' and next == '-': enter line comment
            if ch == '/' and next == '*': enter block comment
        
        handle quote toggling for ' and "
        
        if ch == ';' and not in any quote:
            normalize and save current_chars as a statement
            reset current_chars
        else:
            append ch to current_chars

    save any remaining content as final statement
    return statements
```

**Why two methods:** `sqlglot` provides robust parsing that handles complex PostgreSQL syntax (CTEs, subqueries, dollar-quoting). The fallback ensures the system still works if `sqlglot` is unavailable or encounters syntax it cannot parse.

### 4.2 QEP and AQP Retrieval

**Goal:** Retrieve the optimizer's chosen plan (QEP) and a set of alternative plans (AQPs) that show what happens when specific operators are disabled.

**Algorithm:**

```
function get_qep_and_aqps(connection, query, planner_settings):
    # Step 1: Get baseline QEP
    qep_json = EXPLAIN (FORMAT JSON, COSTS TRUE) query
    qep_total_cost = root_node.Total_Cost

    # Step 2: Generate AQPs
    aqps = []
    for each setting in planner_settings:       # e.g., enable_hashjoin, enable_seqscan
        BEGIN transaction
        SET LOCAL setting TO off                 # Disable one planner method
        aqp_json = EXPLAIN (FORMAT JSON, COSTS TRUE) query
        ROLLBACK                                 # No session state leaks
        
        aqps.append(AQPRecord(setting, aqp_json, cost))

    return PlanBundle(query, qep_json, qep_total_cost, aqps)
```

**Key design decisions:**

- **Transaction isolation:** Each AQP is generated inside a `BEGIN`/`ROLLBACK` block using `SET LOCAL`, which restricts the setting change to that transaction only. This prevents planner settings from leaking between AQP generations.
- **Error resilience:** If an AQP generation fails (e.g., due to an unsupported setting), the error is captured in the `note` field rather than aborting the entire process.
- **10 planner knobs:** The default set covers all major operator categories — 3 join methods, 4 scan methods, plus sort, materialize, and hash aggregate.

**Example:**

For the query `SELECT * FROM customer C, orders O WHERE C.c_custkey = O.o_custkey`:

| Disabled Setting | Resulting Top Join | Total Cost | Ratio vs QEP |
|------------------|--------------------|------------|-------------- |
| (baseline QEP)   | Hash Join          | 18,312     | 1.00x        |
| enable_hashjoin  | Merge Join         | 20,890     | 1.14x        |
| enable_nestloop  | Hash Join          | 18,312     | 1.00x        |
| enable_mergejoin | Hash Join          | 18,312     | 1.00x        |
| enable_seqscan   | Hash Join          | 19,150     | 1.05x        |

### 4.3 Annotation Generation

**Goal:** Produce natural-language annotations that explain *how* and *why* each query component is executed.

**Algorithm:**

```
function generate_annotation(query, bundle):
    # Phase 1: Collect plan information
    scan_notes  = build_scan_notes(query, plan, bundle)   # "Table X is accessed using Seq Scan..."
    join_notes  = build_join_notes(plan)                   # "The Inner join on ... uses Hash Join"
    reasoning   = build_reasoning_notes(bundle, join_ops)  # "Hash Join preferred because..."
    other_notes = build_other_notes(plan)                  # "Sort orders rows by..."

    # Phase 2: Map annotations to SQL lines
    inline_annotations = build_inline_annotations(
        sql_lines, scan_notes, join_notes, reasoning, other_notes
    )

    # Phase 3: Produce output
    return AnnotationResult(
        annotated_query = query + comment block of all notes,
        structured = StructuredAnnotation(sql_lines, inline_annotations, ...)
    )
```

The annotation engine extracts information from the plan tree using four collectors (`_collect_scan_info`, `_collect_join_info`, `_collect_other_ops`) that each perform a DFS traversal via `iter_plan_nodes` and filter for their operator type.

### 4.4 Inline Annotation Mapping

**Goal:** Anchor each annotation to the specific SQL clause it explains, enabling the GUI to highlight relevant lines.

**Algorithm:**

```
function _build_inline_annotations(sql_lines, scan_notes, join_notes, ...):
    # Find clause line ranges
    from_range  = find_clause_range(sql_lines, "FROM",  stop_at=["WHERE","GROUP","ORDER",...])
    where_range = find_clause_range(sql_lines, "WHERE", stop_at=["GROUP","ORDER",...])
    group_range = find_clause_range(sql_lines, "GROUP", stop_at=["HAVING","ORDER",...])
    order_range = find_clause_range(sql_lines, "ORDER", stop_at=["LIMIT",...])
    select_line = find_sql_line(sql_lines, "SELECT")

    # Map notes to ranges
    scan_notes       → FROM clause range       (category: scan)
    join_notes        → WHERE clause range      (category: join)
    reasoning_notes   → WHERE clause range      (category: reasoning)
    "sort" notes      → ORDER BY range          (category: sort)
    "aggregate" notes → GROUP BY range          (category: aggregate)
    other notes       → SELECT line             (category: filter)

    return list of InlineAnnotation objects
```

`_find_clause_range` uses keyword-based scanning: it locates the start keyword, then scans forward until it hits a stop keyword (the next SQL clause) or the end of the query.

### 4.5 Cost-Based Reasoning

**Goal:** Explain *why* the optimizer chose a particular join strategy by comparing costs against alternatives.

**Algorithm:**

```
function _build_reasoning_notes(bundle, qep_join_ops):
    baseline_cost = bundle.qep_total_cost
    notes = []

    for each unique join operator OP in qep_join_ops:
        # Find what happens when OP is disabled
        setting = OPERATOR_TO_SETTING[OP]       # e.g., "enable_hashjoin"
        aqp = find_aqp(bundle.aqps, setting)
        ratio = aqp.total_cost / baseline_cost

        # Collect costs of disabling OTHER join methods
        other_costs = []
        for each ALT_OP in {Nested Loop, Hash Join, Merge Join} - {OP}:
            alt_aqp = find_aqp(bundle.aqps, OPERATOR_TO_SETTING[ALT_OP])
            alt_ratio = alt_aqp.total_cost / baseline_cost
            if alt_ratio > 1.05:
                other_costs.append((ALT_OP, alt_ratio))

        if ratio > 1.05:
            note = "OP is preferred. Disabling it increases cost by ratio×."
            if other_costs:
                note += "Similarly, disabling ALT increases cost by alt_ratio×."
        else:
            note = "OP and alternative have similar costs; choice depends on data distribution."

        notes.append(note)
    return notes
```

**Example output:**

> Hash Join is the preferred join strategy. Disabling it increases estimated cost from 18,312.00 to 20,890.00 (1.1x). Similarly, disabling Nested Loop increases cost by 12.5x; disabling Merge Join increases cost by 1.1x.

## 7. Limitations

### 7.1 Single-Query Scope
The system processes one SQL query at a time. It does not analyze query batches, stored procedures, or transaction-level interactions between queries.

### 7.2 SELECT-Only Annotations
The inline annotation mapping (`_build_inline_annotations`) is designed for SELECT queries. INSERT, UPDATE, DELETE, and DDL statements may produce partial or missing inline annotations, though the plan tree and AQP comparison still function.

### 7.3 Estimated Costs Only
All cost comparisons use PostgreSQL's **estimated** costs from `EXPLAIN` (not `EXPLAIN ANALYZE`). Estimated costs can differ significantly from actual runtime, especially with outdated statistics or skewed data distributions.

### 7.4 One Setting at a Time
AQPs are generated by disabling **one** planner setting at a time. The system does not explore combinations of disabled settings (e.g., disabling both `enable_hashjoin` and `enable_sort` simultaneously), which limits the space of alternative plans explored. The Custom AQP tab partially addresses this by allowing manual multi-setting toggling.

### 7.5 Clause Mapping Heuristics
The SQL clause range finder (`_find_clause_range`) uses keyword-based scanning, which may misidentify clause boundaries in complex queries with subqueries or CTEs where keywords like `WHERE` or `ORDER` appear at multiple nesting levels.

### 7.6 Limited Subquery Support
While the plan tree correctly shows operators for subqueries, the annotation engine maps all scan/join notes to top-level FROM/WHERE clauses. Annotations for operators inside subqueries may be anchored to incorrect SQL line ranges.

### 7.7 No Parallel Plan Analysis
The system does not specifically annotate parallel query execution details (e.g., Gather/Gather Merge worker counts), though these nodes are visible in the plan tree.

### 7.8 PostgreSQL-Specific
The system is designed for PostgreSQL. The `EXPLAIN` JSON format, planner settings, and plan node types are PostgreSQL-specific and would require adaptation for other DBMS platforms.

### 7.9 Graphviz Dependency
The visual plan tree requires the Graphviz system binary to be installed separately from the Python package. Without it, the GUI falls back to a text-only tree representation.

### 7.10 Schema Qualification
The table/alias extraction handles schema-qualified names (e.g., `tpch.customer`) via `sqlglot`, but the regex fallback may not correctly parse all schema-qualified patterns in complex FROM clauses.
